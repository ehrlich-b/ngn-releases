## Bounds callout — [0,+6], NOT the T-item [-3,+3]

**This is a certification, so elo0/elo1 differ from the per-change T-item template.** The recent T-item runs
(T4c, T16) used `-elo0 -3 -elo1 3` (a "better-or-worse-than-immediate-base" test). The batch-certification
decision rule (CLAUDE.md 2026-07-01, batch-ledger.md, and the verbatim rule above) is **SPRT [0, +6]** —
H0: elo<=0, H1: elo>=6. So the cert command sets **`-elo0 0 -elo1 6`**. `alpha=beta=0.05` still yields pLLR
bounds **+/-2.94** (the bounds depend only on alpha/beta, not on elo0/elo1), matching "bounds +/-2.94" in the
rule. Everything else in the command is the box-standard T-item line verbatim, with the binary names swapped
(`ngn_cert.exe` / `ngn_ea69ad6.exe`) and the out-file `cert_out.txt`. Expected header parse:
`H0: elo<=0.0 H1: elo>=6.0 (alpha=0.05 beta=0.05 -> LLR bounds [-2.94, 2.94])`.

### Two earlier same-day headless launch failures (root cause, for the record)

Two earlier same-day attempts to fire this run over SSH failed to start any worker. Root cause: after the
box's Jul-15 reboot there was **no interactive desktop session**, and `boxsprt.sh`'s `schtasks` launcher
creates the task as *run only when user is logged on* — with no interactive logon token, `schtasks /run`
returns success but the batch process never materializes (the create→run→delete completes and spawns
nothing). `boxsprt.sh ps` stayed empty on both attempts. This is the schtasks interactive-token limitation,
not a config error in the command.
