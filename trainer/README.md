# NGN-owned NGNN1/2/3 trainer

Python 3.12, NumPy, and PyTorch are the only runtime dependencies. All trainer
code and fixture weights are written/generated by NGN from the shared
NGNP1/NGNN1 specification. Positions may also come from permitted public data;
no external chess or training toolchain is imported by the trainer. Run modules
from the repository root on a host suited to the workload.

## Local setup

Use a Python environment with NumPy and PyTorch installed. Set `PY=python3`
and run modules from the source root. Training requires suitable compute;
small synthetic fixtures are sufficient for arithmetic checks.

## Data and training

NGNP1 shards contain **raw records with no header**, exactly 32 bytes each.
Offsets: occupancy uint64 at 0; packed piece nibbles at 8; white score int16
at 24; white result byte at 26; STM byte at 27; ply uint16 at 28; flags byte
at 30; reserved byte at 31. Numeric fields are little-endian. Packed pieces
follow occupied squares in ascending order, low nibble first. A record has
at most 32 pieces. Reserved bytes and inactive piece nibbles are ignored.

The reader maps all matching shards read-only, validates their records, and
filters flags before shuffling. By default `--drop-flags 0x0f` drops records
in check, with a best-move capture/promotion, or with a clamped/mate score.
`--drop-flags 0` retains them; `--min-ply N` applies an optional minimum ply.
Shuffle blocks (default 262144 records) and records within each block are
shuffled independently. This bounds memory while visiting every accepted
record exactly once per pass, including a partial last batch. It is not a
uniform global permutation; increase `--block-records` for more mixing.
One CPU prefetch thread overlaps shard reads with GPU work.

`--data-format archive` reads the published STM-normalized ChessBoard 32-byte
layout directly, without copying or converting the file. Its packed piece
colors are 0..5 for the side to move and 8..13 for its opponent; byte 27 is
the own king square and byte 28 is the opponent king square in the opponent's
perspective. The NGN reader converts bounded blocks in memory, validates both
kings and preserves the STM-relative i16 score and result byte. Original STM,
castling and EP are absent; the canonical board treats the moving side as White.
The T80 `corpus-a1` gather manifest says its scores already passed through the
recorded knots mapping to NGN's score/400 scale. Do not apply that mapping twice.

Archive training automatically reserves a seeded board-content hash partition
for validation: `--archive-holdout-modulus 1024` (default) reserves approximately
1/1024 of positions; `--archive-split-seed` defaults to the training seed.
Scores/results and unused padding do not affect partitioning, so duplicate
model inputs cannot cross training and holdout. Initialization scans the board
bytes to count both partitions exactly and stores sparse indexes in RAM.
Training and validation share the read-only maps; no full-corpus output is
written. The finite holdout is cached lazily in RAM (32 bytes per reserved row)
after its first read; training blocks remain a direct stream. Every validation
epoch visits all reserved rows. Archive data has no
NGNP flags/ply, so custom NGNP filters, `--record-counts` and
`--validation-data` are rejected. Split metadata is stored in the checkpoint
and compared during resume.

```bash
"$PY" -m trainer.train --data /path/to/corpus-a1/train-archive.bf \
  --data-format archive --archive-split-seed 20261006 \
  --format 2 --hidden 256 --buckets 8 --threads 2 --k 400 \
  --keep-best-only --out /path/to/owned-t80-run
```

Pass disjoint held-out shard globs with `--validation-data` to log a full
float32 validation loss after every epoch. Validation uses the same filters
and objective, includes the final partial batch, and never updates weights.
History also records loss at lambda=0.75 and pure game-result loss (lambda=0)
from the same predictions, so trials with different training objectives can
be compared. These are probability MSE values, with float64 batch aggregation.

For owned self-play, `--ngnp-holdout-modulus 1024` instead reserves about
1/1024 of eligible records by occupied-board content, across all selected
shards. `--ngnp-split-seed` defaults to the training seed. Duplicate boards
stay together even when their score, result, STM, ply, flags or inactive packed
padding differ. This is a board holdout; adjacent game positions and symmetry
equivalents can still enter different partitions. The original shard-based
validation remains the default (`--ngnp-holdout-modulus 0`). Content splitting
cannot be combined with `--validation-data` or archive input.

Both partitions share read-only maps and apply the same flag/ply filters.
The split uses bounded blocks, records exact raw/eligible/train/holdout counts,
and visits every held-out record, including partial batches. Snapshot prefixes
from `--record-counts` are supported; later appends do not change either
partition. Checkpoints bind the split seed, modulus and receipt during resume.
Keep selected prefixes immutable, as for ordinary NGNP training.

For growing training shards, pass `--record-counts /path/counts.json`: a JSON
object mapping every selected training shard path to its snapshot record count.
Snapshot each byte length once and use `length // 32`. The reader maps only that
prefix, ignores later appends/partial tails, and rejects short files or missing
or extra manifest paths. Resume checks the actual cap values. Validation shards
must be separate, closed files; no data copies are required.

```bash
"$PY" -m trainer.train --data 'data/pilot/*.ngnp' \
  --hidden 256 --batch 16384 --lr 0.001 --epochs 10 \
  --decay cosine --wdl 0.75 --k 400 --out data/own-trainer-run
```

Inputs are transferred as packed bytes; GPU decoding constructs both dense
768-feature perspectives. The feature transformer and output parameters
remain float32. CUDA training defaults to bfloat16 matrix operations, with
float32 probabilities/loss (`--precision fp32` disables autocast).
Training uses eager execution.
`--threads` defaults to four. The GPU is shared: check availability before
starting a run and never stop another session's processes.

The network applies the shared vertically flipped black perspective,
SCReLU activation, and STM-ordered output. The loss is MSE between
`sigmoid(eval_cp/K)` and
`lambda*sigmoid(score_stm/K)+(1-lambda)*result_stm`, with result mapped to
0/0.5/1. AdamW applies weight decay only to W1 and O. Every optimizer step
clips weights/biases to their quantization bounds, including `|O| <= 1.98`.

`--superbatches` aliases `--epochs`. By default an epoch visits all filtered
data. `--positions-per-superbatch N` (also `--positions-per-epoch`) stops
after N positions or cycles through new shuffled passes when N exceeds the
dataset. `--decay step --decay-steps 1000 --gamma 0.5` halves LR every 1000
updates; `--decay none` fixes it. Cosine decay uses the total update count
and ends at `--min-lr-ratio` (default 0.1) of the initial LR.

Each epoch writes `epoch-NNNN.pt`, `epoch-NNNN.nnue`, and updates
`history.json`. The `.pt` file contains model/optimizer state, objective and
data configuration, epoch/update counters, loss history, and RNG states.
`--keep-best-only` instead retains `latest.pt/.nnue` and `best.pt/.nnue`,
selecting the best by validation loss at the training lambda (or training loss
when there is no holdout). All epochs remain in `history.json`.
Resume at an epoch boundary with the same options plus
`--resume /path/epoch-NNNN.pt`. `--epochs` is the total desired count, not
additional epochs. Cosine resume requires the original total count; step
or fixed schedules permit increasing it. Training-relevant options and
record counts are checked on resume. Keep shards immutable for reproducible
continuation. Write to a distinct output directory for separate runs.
History is atomically published and restored from the selected checkpoint on
resume, even when that checkpoint has already reached the desired epoch count.

Epoch throughput includes reads, shuffle, transfers, feature construction,
forward/backward, AdamW, and clipping, but excludes shard validation and
checkpoint/export writes. A separate steady rate excludes the first ten
updates. Both rates are logged.

## Export and exact integer evaluation

```bash
"$PY" -m trainer.export /path/epoch-0001.pt /path/network.nnue
"$PY" -m trainer.refeval /path/network.nnue \
  '8/8/8/8/8/8/4Q3/4K2k w - - 0 1'
"$PY" -m trainer.refeval /path/network.nnue --fen-file /path/fens.txt
```

Export uses nearest-integer rounding with ties to even, checks finite/range
and shape constraints, and writes little-endian NGNN1 with IEEE CRC32.
H is any multiple of 16 from 16 through 2048. The 24-byte header is magic
`NGNN`, then uint32 version/H/QA/QB/SCALE (1/H/255/64/400). It is followed
by row-major W1 int16 [768,H], B1 int16 [H], O int16 [2H], OB int32,
then uint32 CRC32 over all preceding bytes. Files are atomically replaced.

`--buckets NB` accepts 1 (default), 2, 4, or 8. NB=1 retains the original
parameter shapes and NGNN1 export unless `--format 2` is requested. Multiple
buckets require/export NGNN2; `--format 1 --buckets 8` is rejected. The export
CLI accepts the same `--format` override and otherwise preserves the checkpoint
format (or infers it from output shapes for older checkpoints). Resume validates
NB and format; old NGNN1 checkpoints default to NB=1/format=1.

NGNN2 has a **28-byte header**: magic `NGN2`, then little-endian uint32
version/H/NB/QA/QB/SCALE (2/H/NB/255/64/400), followed by W1 int16 [768,H],
B1 int16 [H], O int16 [NB,2H] in bucket order, OB int32 [NB], and IEEE CRC32
over every preceding byte. W1/B1, activation, quantization, and both truncating
divisions are identical to NGNN1. NGNN2 with NB=1 and the same quantized
parameters produces exactly the same integer evaluation as NGNN1.

Count **all pieces including both kings**. The exact bucket formula is
`b = min(NB-1, (popcount(occupancy)-2)*NB//32)` with integer division; Go uses
`/32`, which agrees for valid positions (at least two pieces). For NB=8,
counts 2..5 select 0, 6..9 select 1, ..., 30..32 select 7. Positions above
32 pieces saturate at NB-1; malformed positions with fewer than two pieces
defensively select zero. Trainer decoding sums the decoded occupancy bits and
computes the indices on the GPU, with no CPU count transfer. Only the selected
output row/bias receives gradients. The Go evaluator selects from current board
occupancy on every evaluation, so captures, undo, and null moves need no new
accumulator state. Its existing AVX2 kernels receive the selected row slice.
Both loaders validate magic/version, H/NB, constants, exact length, and CRC
before exposing weights; UCI and `datagen -net` accept both formats.

```bash
"$PY" -m trainer.train --data 'data/pilot/*/*.ngnp' \
  --hidden 256 --buckets 8 --epochs 1 --out data/ngnn2-smoke
"$PY" -m trainer.make_random_net --buckets 8 \
  --out testdata/ngnn2/random_h32_b8.nnue \
  --evals testdata/ngnn2/random_h32_b8_evals.json
```

The reference evaluator depends only on NumPy/stdlib, validates length,
header, and CRC, widens all arithmetic to int64, and performs **two**
truncating integer divisions in the specified order. Accumulators may
exceed int16; output sums may exceed int32. Given the format's maximum H,
all arithmetic fits int64 even at the int16 endpoints. FEN parsing ignores
castling/en-passant/counters, because this network uses only pieces and STM.
`Network.evaluate_record()` accepts a decoded NumPy NGNP1 record.

### Bounded exported-integer validation diagnostic

`trainer.quantized_validation` measures the actual NGNN3 export using the
independent integer reference, including mirrored king inputs, STM ordering,
SCReLU saturation, both signed truncating divisions and the engine cp clamp.
It needs only NumPy and accepts precomputed **STM-relative cp** from the same
float checkpoint, before export, as one JSON number or `null` per line.

```bash
python3 -m trainer.quantized_validation \
  --network epoch-0001.nnue --records selected-validation.ngnp \
  --float-predictions validation-float-cp.jsonl --max-records 32 \
  --lambda 0.75 --k 400 --out integer-diagnostic.json
```

Supply the existing held-out stream, in its existing order, with exactly the
same flag/ply filters, board split and lambda/K used by float validation.
The CLI's raw NGNP1 file must already contain those selected records; it does
not select or filter a partition. The Python `evaluate_stream` API accepts an
iterable of NumPy NGNP1 records directly, so an existing holdout reader can
supply records without materializing the corpus. The mandatory positive cap
consumes no lookahead record or prediction; memory is independent of stream
length. JSONL predictions must remain aligned even where unknown (`null`).
Absent/exhausted predictions also remain unknown. Empty metrics are `null`.

The report includes counts, integer probability-MSE loss on all processed
records, paired float/integer losses and their difference, and signed/absolute/
squared cp-error sums and means (plus RMSE and max absolute error), overall
and for every existing material output bucket. Both differences are **integer
minus float** and use only records with known float predictions. Loss uses
`(sigmoid(cp/K) - (lambda*sigmoid(score_stm/K)+(1-lambda)*result_stm))^2`,
matching the float objective. QA=255, QB=64 and score scale=400 are recorded
separately from the configurable sigmoid K.

This is a separate diagnostic: existing float validation metrics, splits,
checkpoint selection and default play are unchanged. Never select checkpoints
on claim games. Historical integer-validation diagnostics are outside this source archive; run
`python3 -m unittest trainer.tests.test_quantized_validation` for its controls.
A full H768 corpus diagnostic and any play decision require a completed training
job; synthetic fixture success establishes no Elo improvement.

## NGNN3 king inputs

`--format 3 --kb-map default` uses eight input buckets and preserves NGNN2's
material output buckets (`--buckets 1/2/4/8`). First vertically flip squares
for Black (`s XOR 56`). If the oriented own king is on files e–h, horizontally
mirror every square for that perspective (`s XOR 7`). Look up the resulting
king square in the file's 64-byte map. NGN's default on files a–d is:

| Oriented rank | a,b | c,d |
| --- | --- | --- |
| 1 | 0 | 1 |
| 2 | 2 | 3 |
| 3 | 4 | 4 |
| 4 | 5 | 5 |
| 5–6 | 6 | 6 |
| 7–8 | 7 | 7 |

The other half of the default table reflects these entries; runtime lookup
always follows mirroring. Feature index is `bucket*768 + rel*384 + T*64 + s`,
with `rel=0` for own pieces, `1` for opponent pieces, and T=0..5 for
pawn/knight/bishop/rook/queen/king. Both kings are features. W1 is [KB*768,H];
B1, SCReLU, output selection, integer divisions and quantization are unchanged.

All fields are little-endian: magic `NGN3`; seven uint32 fields
`version=3,H,KB,NB,QA=255,QB=64,SCALE=400`; 64 uint8 map entries;
W1 int16 [KB*768,H], B1 int16 [H], O int16 [NB,2H], OB int32 [NB];
IEEE CRC32 of everything preceding it. Header length is 96 bytes. KB=1..8,
all map entries must be below KB; H and NB retain existing bounds. A JSON
array of 64 IDs supplied as `--kb-map path.json` chooses another layout;
export stores the actual map and resume compares its contents. The GPU builds
both bucketed feature vectors directly from packed records. NGNN3 shard
validation requires exactly one king of each color.

Optional `--king-factorizer` learns shared [768,H] feature rows plus the usual
king-bucket residual rows. It requires NGNN3 with at least two input buckets.
Shared rows start at zero, preserving the original initialization and RNG;
AdamW updates/decays both components. Forward uses their float32 sum. Export
folds that same sum before quantizing once into the unchanged NGNN3 layout,
so inference needs no additional parameters or computation. Clipping bounds
the merged rows, with residual bounds relative to the shared component.

Factorized checkpoints retain both tensors and bind the flag on resume;
changing it is rejected. Legacy checkpoints without the flag remain ordinary
models. This capability has CPU gradient, clipping, export, resume and integer
parity controls. Run its CUDA FP32/BF16 control before a real training trial:
`python -m unittest trainer.tests.test_king_factorizer.KingFactorizerTests.test_cuda_forward_gradients_and_bf16_step -v`.
No playing-strength improvement is established by tooling checks.

Optional `--fake-quantize` requires `--format 3` and enables export-exact
forward values with straight-through round/truncation gradients. Shared rows
merge before rounding; the opt-in path uses float64 integer-valued arithmetic
with mixed precision disabled, then returns float32 cp. Both signed divisions,
SCReLU saturation and the final cp clamp match the NGNN3 integer reference.
The original float path remains `model.forward_float(...)`; default training
is unchanged. The flag is bound on resume (legacy checkpoints default false).
Run the small CPU control with
`python -m unittest trainer.tests.test_quantized_forward`. This is
an arithmetic fixture, with no H768 throughput or playing-strength claim.

Workers own caches keyed by perspective, bucket and mirror state. A king move
that changes either context refreshes only the moving side from the cached
accumulator by subtracting removed piece squares and adding new ones. The
opponent remains incremental. Same-context king moves, castling rook changes,
captures, en passant and promotions use the ordinary fused row kernels.
Undo restores the stack without rewinding the cache; cache bitboards describe
their own last position. Null moves copy the accumulator. Reset can reuse the
cache; selecting another network creates new worker state.

```bash
python -m trainer.train --data 'data/pilot/*/*.ngnp' \
  --format 3 --kb-map default --hidden 256 --buckets 8 --epochs 1 \
  --out data/own-nnue3-smoke
python -m trainer.make_random_net --format 3 --kb-map default --seed 20261006 \
  --hidden 32 --buckets 8 --out testdata/ngnn3/random_h32_k8_b8.nnue \
  --evals testdata/ngnn3/random_h32_k8_b8_evals.json
```

Existing loader/selection APIs and UCI EvalFile accept all three formats;
NGNN3 reports backend `ngnn3`. NGNN1/2 retain their feature and weight layouts.

## Archives on another campaign host

`--data-format archive` also accepts a local `*.archive.json` descriptor with
`url`, `bytes`, and lowercase `sha256` fields. The serving host verifies the
file digest before publishing and uses the quoted digest as its ETag. Each read
requires an exact HTTP206 byte range, matching size and ETag. Changes or short
reads fail before records reach the model. Requests cover one existing archive
block; neither training nor validation copies the corpus to local disk.

The descriptor participates in the same sorted source list, content split,
block shuffle and batching as ordinary archives. A descriptor substituted for
the corresponding file produces identical batches when source order is kept.
Resume binds its size and digest in the archive split receipt. Source ordering
is part of the training recipe and must be frozen in the manifest.

`python -m trainer.archive_server` serves files listed in a private campaign
directory's `files.json`, with each entry containing `bytes`, `sha256`, and
`mtime_ns`. Use an access token file and an explicit LAN bind inside the host's
CPU and memory scope. `--uploads` permits initial transfer into that server directory;
stop the upload server after transfer and retain the read service for training.
URLs containing tokens and private descriptors stay out of Git and public logs.

NGNN6 residual training uses `--format 6 --residual-source OWNED.ngn3
--hidden 768 --buckets 8 --precision fp32` (H32 is reserved for fixtures).
The source supplies the exact inherited trunk, linear head and king map. The small owned source, records, weights and expected results for CPU
reproduction are under `experiments/wave2-1104/residual-{convert,trainer}/`;
`trainer.tests.residual_fixture` defines the two-step fixture recipe.
### NGNN5 threat training

Use `--format 5` with the NGNN3 king map and output buckets. Threats are directed
occupied attacks by the perspective's own pieces, including friendly defenses;
sliders stop at the first blocker. Tensor decoding applies the same rank flip,
king-file mirror, king bucket and 42564-row geometry as the engine. Packed row
indices feed summed embedding bags, so no dense threat-feature matrix or
`[edges, hidden]` activation is allocated. Float32 threat parameters are learned
with AdamW, clipped to `[-128/255, 127/255]`, and exported as sparse int8 rows.
The piece transformer remains int16. Export to earlier formats rejects threats.

Initialize from an NGNN3 checkpoint with `--warm-start checkpoint.pt`; specify
matching `--hidden`, `--buckets`, `--kb-map` and `--king-factorizer`. This loads all
NGNN3 coefficients, zeros threats, and starts a new optimizer and schedule.
`--resume` instead restores a same-format training run and is mutually exclusive
with warm start. CPU training enables deterministic algorithms so checkpoint
continuation preserves exact floating point updates across processes. The CPU fixture test checks NGNN3/5 equality within `1e-6`, both
factorized and ordinary, before any update.

Reproduce the owned, 20-record trained parity fixture with
`python3 -m trainer.make_ngnn5_fixture --out /path/to/scratch`. It uses CPU float32,
H=16, KB=8, NB=8, six AdamW updates and a seeded NGNN3 warm start. The output
contains the input records, checkpoints, exports, training throughput and scalar
integer reference scores. `TestNGNN5TrainerParity` checks the committed small
fixture's hash, training metadata, scores and exact active threat rows. The
embedded default network is unchanged.

Memory planning for B=16384, H=256, KB=8, NB=8, float32 training: piece features
alone occupy 768 MiB. Threat parameters occupy 332.53125 MiB; including their
gradients and both Adam moments costs 1330.125 MiB. All model parameters,
gradients and moments together require about 1354.20 MiB (no factorizer).
Budget an additional 3072 MiB per batch for dense piece features, activations,
backward buffers, packed 32x32 pair indices, masks, sorting and embedding-bag
indices/workspace: about 4.33 GiB total plus framework/allocator overhead.
This is a conservative planning estimate, not a measured peak or a device
capacity guarantee. There is no B*KB*42564 dense threat matrix (41.57 GiB at this
batch size). AdamW implementations may need extra parameter-sized temporaries;
allow a further 339 MiB if using foreach rather than sequential CPU updates.
